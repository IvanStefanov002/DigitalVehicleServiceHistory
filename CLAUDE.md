# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Use the Gradle wrapper (`./gradlew` on Unix, `gradlew.bat` on Windows). All commands run from the repo root.

- **Build debug APK:** `./gradlew assembleDebug`
- **Install on connected device/emulator:** `./gradlew installDebug`
- **Full build + checks:** `./gradlew build`
- **Unit tests (JVM, `src/test`):** `./gradlew test` — single class: `./gradlew testDebugUnitTest --tests "com.example.maintenanceapp.ExampleUnitTest"`
- **Instrumented tests (`src/androidTest`, needs device/emulator):** `./gradlew connectedAndroidTest`
- **Clean:** `./gradlew clean`

There is no separate lint/format step configured beyond Android's default `lint` task (`./gradlew lint`).

## Project shape

- Single Gradle module: `:app`. Language is **Java** (not Kotlin), UI is classic **Android Views with XML layouts** (no Compose, no fragments).
- Build config: Gradle Kotlin DSL (`.gradle.kts`) with a version catalog at `gradle/libs.versions.toml`. Add/upgrade dependencies there, not by hardcoding versions — note `okhttp` is currently hardcoded in `app/build.gradle.kts` as an exception.
- `compileSdk`/`targetSdk` 36, `minSdk` 24, Java 11. Package/namespace: `com.example.maintenanceapp`.
- **The app is called „Автодосие“** (`app_name`, used as the launcher label *and* the wordmark on the login screen). The Gradle `rootProject.name` is the Latin `Avtodosie` on purpose, so build artefacts keep ASCII filenames. The directory, the namespace and the `Theme.MaintenanceApp` style names still say MaintenanceApp — cosmetic, but note **`com.example.*` is rejected by Google Play**, so the `applicationId` has to change before any release; doing it after there are installs makes it a new app rather than an upgrade (and it touches the `${applicationId}.fileprovider` authority).

## Architecture

Four Activities (declared in `app/src/main/AndroidManifest.xml`), no fragments:

- **LoginActivity** — launcher activity. On `onCreate` it short-circuits to `MainActivity` if a `username` key exists in the `"auth"` SharedPreferences file. Login POSTs JSON credentials and, on success, stores the returned Bearer `token` plus profile fields (`username`, `fullName`, `email`, `vehicleCount`, `profileImageBase64`) in SharedPreferences. A text button (`btnGoToRegister`) opens `RegisterActivity` through `registerLauncher`.
- **RegisterActivity** — sign-up form (full name / username / email / password / confirm), reached only from the login link; visually mirrors `activity_login.xml` (same photo + scrim + floating card) so the auth pair reads as one screen. **Validation is inline per field** (`TextInputLayout.setError`), not toasts: it marks *every* offending field in one pass and focuses the first, and a `TextWatcher` per field clears the error as soon as the user starts fixing it. Rules: full name required, username ≥3 chars matching `[A-Za-z0-9._-]+`, `Patterns.EMAIL_ADDRESS`, password ≥8, confirm must match. Email is lower-cased before sending so the server's uniqueness check can't disagree with a later login. On 2xx it saves the login-shaped payload to the `"auth"` prefs and goes to `MainActivity` with `NEW_TASK|CLEAR_TASK` — **auto-login**, so the user never retypes what they just chose; the flags matter because `LoginActivity` is still on the stack and Back would otherwise land on a screen that immediately bounces forward again. If the 2xx carries **no `token`** (backend shipped without token issuance) it can't act authenticated, so it degrades to `setResult(RESULT_OK, EXTRA_USERNAME)` + `finish()` and login pre-fills the username. Duplicates are pinned to the field that collided by reading the response's `error` string (`"username"` / `"email"`), falling back to HTTP 409/460. **The POST is not retried** — unlike the idempotent GETs and login, "no reply" doesn't mean "no user" on this server, so a silent retry would either double-create or misreport "username taken" for a name the user does own.
- **MainActivity** — the main shell. A `BottomNavigationView` (**Автопарк** / Поддръжка / Профил — Bulgarian labels) swaps content by **inflating a layout into the `contentContainer` FrameLayout** (`showVehicles`/`showMaintenance`/`showProfile`), rather than navigating between screens or using fragments. Logout clears the `"auth"` prefs and returns to `LoginActivity`. The Home tab (`home_content.xml`) has a header ("Вашият автопарк" + a live `R.plurals.vehicle_count`), the list, and an empty state (`homeEmpty`), all toggled by `refreshHomeSummary()`. Home-tab view refs (`homeAdapter`/`homeRecycler`/`homeVehicleCount`/`homeEmptyState`) are cleared via `clearHomeRefs()` when switching away so async updates don't touch a detached layout.
- **AddVehicleActivity** — full add-vehicle form (photo panel + fields), launched from the Vehicles tab's FAB via an `ActivityResultLauncher`; returns `RESULT_OK` when a vehicle was saved. Root is `#avRoot`; its inset listener unions `systemBars()` with `displayCutout()` (the other screens use `systemBars()` alone) because the status-bar inset can be shorter than a camera notch, which left the back button untappable. Localized to Bulgarian **except its Toast messages**, which are still hardcoded English.
  - **Layout mirrors `activity_add_maintenance.xml`**: three tonal section cards, each headed by an accent icon chip, holding outlined `TextInputLayout`s with floating labels (no `AmLabel` TextViews above fields — that's the older idiom, still used by `activity_edit_vehicle.xml`). The three accents encode real categories, per the Categorical accents rule: **1 = photo**, **2 = Основни данни** (exactly the four fields `saveVehicle()` requires — make/model/year/plate), **3 = Допълнителни данни** (everything with a usable default). Year and plate share a row since a 4-digit year alone wastes the line.
  - Field labels reuse the **`ev_*`** strings shared with `activity_edit_vehicle.xml`, and each field's `startIconDrawable` is the same `ic_*` the detail screen puts on its spec row, so a field looks the same everywhere. VIN carries a 17-char counter; mileage a `суффикс` "км".
  - **Type (`#ddVehicleType`) leads section 2**, before make/model: it decides how the vehicle is grouped on Автопарк and whether the oil advisor will answer for it. Same exposed-dropdown trap as fuel below, so it's seeded with `VehicleType.DEFAULT` in `onCreate`; read back by matching the label (`selectedVehicleType()`), never by position — an autocomplete filters as you type.
  - **Fuel is an exposed dropdown (`#ddFuelType`), not a `Spinner`.** Same trap as `AddMaintenanceActivity`: an autocomplete has no `getSelectedItemPosition()` and **starts with nothing selected**, where a `Spinner` always had item 0 selected — so `onCreate` seeds it via `setSimpleItems(...)` + `setText(fuelTypes[0], false)`, or a user who never opens the dropdown would submit an empty `fuelType`. Read it with `getText()`, not `getSelectedItem()`.
  - The `edt*` fields are `TextInputEditText` now; the Java still types them as `EditText` (a supertype), so `findViewById` needed no change.
  - **Photo panel** — a `MaterialButtonToggleGroup` (`#togglePhotoMode`, `singleSelection` + `selectionRequired`) picks between **Стандартна** (`#btnModeDefault`) and **Моя снимка** (`#btnModeUpload`); `applyPhotoMode(boolean)` shows/hides the picker button and swaps `#txtPhotoHint`. Default mode is checked in `onCreate`, reproducing the pre-panel behaviour: `imageBase64` is sent as `""`, the server stores nothing, and every screen falls back to the vehicle type's own `*_placeholder`.
  - `addOnButtonCheckedListener` fires **twice per switch** (uncheck old, check new), so the callback acts only when `isChecked` — otherwise the panel briefly renders the state the user just left.
  - Switching to default mode **does not discard** an already-picked photo: `pickedPhoto`/`imageBase64` are kept and restored when the user toggles back, and `saveVehicle()` decides what to send from the `uploadPhoto` flag alone. Choosing upload mode but picking nothing sends `""` too — it degrades to the default image rather than blocking the save.
- **VehicleDetailActivity** — opened by tapping a row in the Vehicles list. Receives the selected `Vehicle` as a `Serializable` Intent extra (`EXTRA_VEHICLE`) and displays its full details plus the maintenance schedule. Localized to **Bulgarian** (strings in `res/values/strings.xml`). Header carries **edit** (`btnEdit`) and **delete** (`btnDelete`, tinted `?attr/colorError`) buttons. Delete goes through a `MaterialAlertDialogBuilder` confirm, POSTs `/vehicles/delete`, then `setResult(RESULT_OK)` + `finish()` so `MainActivity` reloads the list; a `deleteInFlight` flag plus disabling the button stop a double-tap from firing two deletes.
- **AddMaintenanceActivity** — "log a service" form, grouped into three tonal section cards. The two pickers are **Material exposed dropdowns** (`TextInputLayout` + `MaterialAutoCompleteTextView`, ids `ddVehicle`/`ddType`), **not** `Spinner`s: an autocomplete has no `getSelectedItemPosition()`, so the vehicle choice is tracked by hand in `selectedVehicleIndex` (two vehicles can share a label, so matching on text is not safe). `setTypeItems(...)` preserves the user's pick when the server catalog lands after they've already chosen from the fallback. `edtCost` is optional and sent **only when filled** — the key is left out of the body entirely, so the server can tell an unrecorded price from a genuine 0; a comma is normalised to a dot before parsing (a Bulgarian keypad offers a comma), and `NaN`/`Infinity` are rejected because `JSONObject.put` would throw on them. `edtDate` is `focusable="false"` and opens a `MaterialDatePicker`, formatted **in UTC** to `yyyy-MM-dd` — the picker returns UTC midnight, so formatting in local time can shift the date by a day. Launched from the Поддръжка tab. Receives the vehicle list as a `Serializable` extra (`EXTRA_VEHICLES`). Loads the type catalog from `GET /maintenance/types` (falls back to a hardcoded Bulgarian list) and `POST`s to `/vehicles/maintenance/add`; returns `RESULT_OK` on success.
- **EditVehicleActivity** — edit form for a vehicle's fields (type/make/model/year/plate/mileage/fuel/vin/color; image not edited here). The type `Spinner` gets its adapter in code from `VehicleType.labels(...)` and is read back by ordinal. Opened by the pencil button (`btnEdit`) in `VehicleDetailActivity`'s header. Prefills from the passed `Vehicle` (`EXTRA_VEHICLE`), `POST`s to `/vehicles/update`, and on success returns the updated `Vehicle` (`EXTRA_RESULT_VEHICLE`) with `RESULT_OK`. The detail screen re-binds from it and itself returns `RESULT_OK` so `MainActivity` reloads the list. `MainActivity.openVehicleDetail` uses `vehicleDetailLauncher` for this.
- **VehicleComplianceActivity** — per-vehicle **документи и валидности** screen (винетка / ГТП / ГО), opened by the tappable `#cardDocuments` row on `VehicleDetailActivity` (not a header button — that header already carries four). Receives `EXTRA_VEHICLE`, returns the updated `Vehicle` as `EXTRA_RESULT_VEHICLE` + `RESULT_OK` when a declared date was saved, same contract as `EditVehicleActivity`. See **Document validity** below — read that before changing anything on this screen, because the two-tier trust model is the whole point of it.

`RecyclerView` lists use `adapter/VehicleAdapter` backed by the `model/Vehicle` POJO (`Serializable`, carries all vehicle fields).

### Vehicle types (car / motorcycle / van / truck)
`util/VehicleType` + the `vehicleType` column on `Vehicle`. Four values, wire form lowercase
(`car`/`motorcycle`/`van`/`truck`), Bulgarian labels in `strings.xml` (`vt_*` singular for pickers
and the detail spec row, `vt_group_*` plural for the Автопарк headers).

- **Absent or unrecognised reads as `car`, everywhere.** Every vehicle predating the column is one,
  and the server may be a build behind. `VehicleType.fromApi` is the only place that rule is
  written — never read `Vehicle.vehicleType` directly, go through `VehicleType.of(vehicle)`.
- **The enum's declaration order is the UI order**: section order on Автопарк, item order in both
  pickers. It's "most common first", not alphabetical. `VehicleType.labels(ctx)` builds the picker
  arrays from the enum rather than from a `string-array`, so a spinner position can't drift from the
  enum on one screen and not the other (the edit screen sets its `Spinner` adapter in code for
  exactly this reason — no `android:entries`).
- **`supportsOilAdvisor()` is the single home of the car-only rule.** Motorcycle oil is a different
  product (wet clutch, JASO MA rather than ACEA/OEM approvals) and a truck's different again, so a
  car spec shown for either would be *confidently wrong* — the one failure mode the oil advisor
  exists to avoid. Both call sites filter (`MainActivity`'s `#cardOilAdvisor` for the "no cars" toast,
  `OilRecommendationActivity` again on the way in, so a wrong caller can't put a bad answer one tap
  away). **Maintenance types stay common to all vehicle types on purpose** — the catalog is not
  filtered and `AddMaintenanceActivity` still receives the whole fleet.
- **Автопарк groups by type with headers, and headers appear only when the fleet holds more than one
  type.** `VehicleAdapter` now builds a flat `rows` list (header | vehicle) in `rebuildRows()`, with
  two view types; a lone „Автомобили“ band over an all-car list separates nothing. Grouping is
  client-side from the list already in memory — no filtered list route.
- **The header count uses `vehicle_count_mixed` („превозни средства“) as soon as the fleet isn't
  all cars**; counting a motorcycle as an „автомобил“ is wrong in the one place the user counts.
- **Each type carries its own list placeholder** (`placeholderRes`) as well as its header/spec glyph
  (`iconRes`) — see the Images section under **Networking** for why those two can't be the same
  drawable.
- **`requiresVignette()` is the vignette exemption**, false for `MOTORCYCLE` (BG exempts category L
  from the road-network toll). All three vignette callers check it and **skip the request**:
  `VehicleComplianceActivity.fetchVignette`, `MainActivity.loadDocumentStatuses` and
  `ServiceReminderWorker`. The reason it can't just be left to fetch: the authority's answer for a
  bike is a perfectly correct „no vignette“, which `ofVignette` maps to `OVERDUE` — badging the bike
  red forever and notifying nightly about a document its owner isn't required to hold. Same family of
  rule as "a failed check is unknown, never expired": **the app must not manufacture a violation.**
  The compliance card renders an exempt branch instead — neutral grey pill (`cmp_st_exempt`), the
  reason where the date goes, **no buttons and no provenance label** (no check was made, so neither
  „официална“ nor „декларирано“ is true). The card is not hidden: "what about the vignette?" is a
  question the user came to that screen with.
- **Trucks are left as vignette-required even though it isn't always true.** Over 3.5 t a goods
  vehicle pays the distance-based ТОЛ instead, but the cutoff is a weight the app doesn't store, so
  the type alone can't decide. Showing the authority's own vignette answer is the lesser error;
  fixing it properly means asking for the weight, not inferring from „камион“.
- Still not handled: **ГТП periodicity differs by type**, which only the „+1 година“ renewal
  shortcut would need to know.
- Backend contract: `docs/backend-vehicle-type-task.md` — **not implemented server-side yet**, so a
  type set in the app is lost on the next `GET /vehicles` until it lands.

### Vehicle data flow (important)
`MainActivity` holds an **in-memory cache** (`List<Vehicle> vehicles`) that is the source of truth for both the Vehicles list and the Profile count. It is loaded **once per session** in `onCreate` via `loadVehicles()`, and reloaded **only after a change** (Add Vehicle returning `RESULT_OK`) — **not** on tab switches. Both tabs render from this cache, so switching tabs makes no network calls. Mutations (add / edit / delete) all trigger `loadVehicles()` via their `RESULT_OK`; add any future mutation the same way.

**`fetchVehicles` failure is `null`, not empty.** `deliverError` delivers `null` to the callback so "the user has no vehicles" stays distinguishable from "the server was unreachable", and `loadVehicles()` keeps the cached list on `null`. Do not "simplify" this back to an empty list: it used to blank the whole fleet out (and show the empty state) on any transient failure, which pull-to-refresh turns from a rare startup glitch into a routine one.

### Document validity (винетка / ГТП / ГО)
`VehicleComplianceActivity` + `util/ComplianceStatus` + `model/VignetteInfo`. **The one rule that governs this feature: two tiers of trust live on one screen, and the UI must never blur them.**

- **Tier 1, verified — the vignette only.** `GET /vehicles/vignette?id=` hits our backend, which proxies (and caches) the National Toll Administration's public plate check at `check.bgtoll.bg`. Authoritative, so no user input exists for it.
- **Tier 2, declared — ГТП and ГО.** Dates the user types in. **These cannot be automated and that is not an oversight.** АА's inspection check (`rta.government.bg/.../checkinsp.php`) and the Guarantee Fund's ГО check are both behind a **server-enforced CAPTCHA** — verified by POSTing without one: the former returns `{"validation":{...,"captchaValid":false,...}}`, the latter re-renders the page with „Грешен код“. Neither offers an official API. **Do not add a captcha-solving path**; the sanctioned routes are a written request to the Fund's Информационен център or eGov.bg with a ПИК.
- Provenance is load-bearing UI, not decoration: `cmp_src_official` / `cmp_src_declared` on every card plus `cmp_footnote`. Deleting or genericising those strings is what turns this screen into a lie.
- Tier 2's compensation is the **Провери** button — it opens the official page *and copies the vehicle identifier to the clipboard*, because none of the pages accept it as a URL parameter. **ГТП points at RTA's newer EIS `public-vehicle-check/vin-check` page and copies the VIN** (that page is VIN-keyed), and is the one check that opens *in-app* — see **Assisted document check**. **ГО copies the VIN too**, falling back to the plate when none is stored (the Fund accepts either and says the VIN gives the fullest result), and opens in the **browser** — its WebView was removed, see **Why ГО is a link-out**. The vignette-purchase link copies the plate. `openExternal(url, copyValue, copiedMsgRes)` takes the value + toast per caller rather than assuming the plate. (Toast suppressed on API 33+, where the system shows its own copy confirmation.) RTA also exposes a JSON API behind that page but it is reCAPTCHA-gated (misconfigured — token unverified); we do **not** forge it, we asked for authorised access — `docs/rta-access-request-email.md`.
- **The vignette card's „Провери“ appears only when the check came back unknown** (`URL_CHECK_VIGNETTE` → `https://check.bgtoll.bg/#/vignette`, opened in the browser with the plate copied). Three deliberate constraints on it:
  - **It writes nothing back.** Tier 1 is machine-verified with no user input anywhere; a date the user typed after reading that page would be declared data wearing the `cmp_src_official` label. Read-only link-out, and it must stay one.
  - **Only in the unknown state.** On a `VALID`/`NONE` answer the app already knows, and offering a re-check invites second-guessing the authority. `NONE` gets the buy button instead. Same philosophy as the renewal row being DUE/OVERDUE-only.
  - **Not `web.bgtoll.bg/TollProduct`** — that's the purchase checkout (`__RequestVerificationToken` + reCAPTCHA), the one page here that is captcha-gated. And **not a WebView**: hosting a page in-app is only justified by a captcha needing a human, this page has none, and its bundle reads no query params, so it would mean injecting JS into another React SPA for nothing. Note the `#/` — hash router; plain `/vignette` 404s.
  - Tempting and still rejected: having the **client** call `check.bgtoll.bg`'s public API directly when our proxy fails. It gives up the server-side cache that keeps our volume courteous on an undocumented third-party endpoint, points every device at it, and loses the property that breakage there is fixable by a deploy instead of an app update.
- **Three vignette outcomes, not two.** `VALID` and `NONE` are both real answers from the authority; a failed request is *unknown* and arrives as `vignette == null` + `vignetteFailed`. Rendering unknown as `NONE` would announce a lapsed vignette on every network hiccup — the same mistake the `fetchVehicles` null-vs-empty rule exists to prevent. `ComplianceStatus.of(...)` returns `null` for the same reason, and `null` means **unknown, never fine**.
- **Due-soon windows are per-document** (`VIGNETTE_DUE_DAYS` 7, inspection/insurance 30, instalment 14). One shared 30-day window would leave a weekend vignette “expiring” for its entire life.
- **ГО tracks the next instalment separately from the policy expiry**, and the card's pill shows the *worse* of the two. A missed instalment terminates cover mid-term, so an “expires in March” reminder would otherwise stay silent through it.
- `ComplianceStatus.daysUntil` works in the **local** calendar, unlike `AddMaintenanceActivity`'s UTC formatting. Both are right: the picker hands back UTC midnight (a string/millis conversion), while “how many days from today” is a question about the user's day, and in UTC+3 those disagree for the first hours of every date.
- The three declared dates are **plain vehicle columns**, carried by the existing `GET /vehicles` and `POST /vehicles/update` rather than an endpoint of their own — which is why `Vehicle.toUpdateJson()` now exists. That route rewrites every column, so a hand-rolled body at either call site would blank the fields the other screen owns; both go through the model. `imageBase64` is deliberately excluded from it.
- The detail screen's entry row shows a warning glyph but **no OK state and no vignette input** — it only knows the declared dates, so its silence means “nothing you told us is expiring”, never “this car is road-legal”.
- Icon chips use accent 1 / 3 / 5 and **skip amber and green on purpose**: those are the DUE and OK status colours, and a green chip beside a red “expired” pill reads as a contradiction.
- **Wired into the fleet surfaces (2026-08-18).** `ComplianceStatus` owns the four due-soon windows (`VIGNETTE_DUE_DAYS` 7, inspection/insurance 30, instalment 14) plus `declared(Vehicle)` and `ofVignette(VignetteInfo)`; the compliance screen, the detail row glyph, the Автопарк badges and the reminder worker all derive status from those, so a badge and a notification about the same car can never disagree. See **Document reminders** below.

### Categorical accents
Beyond the single-hue M3 scheme there's a 5-entry **categorical palette** (`accent_1_fg`/`accent_1_bg` … `accent_5_*`, defined per-mode in `values(-night)/colors.xml`) exposed as indexable `array/accent_fg` + `array/accent_bg` in `values/arrays.xml`. Used by the three section headers on the add-service form, where each accent marks a *different kind* of information. **Don't rotate it per item in a list.** That was tried on the Поддръжка type grid and reverted: every card there shows the same wrench meaning the same thing, so varying its tint implied a distinction that doesn't exist. Use an accent to encode a real category, not to add variety for its own sake. Keep the two arrays the same length and order — index N of one pairs with index N of the other. Fetch with `getResources().getIntArray(...)`, which resolves the current light/dark values.

### Pull-to-refresh
The three tabs and the detail screen are wrapped in a `SwipeRefreshLayout`; forms deliberately are not (a pull would fight the user's input). Spinners are themed centrally by **`util/SwipeRefresh.theme(...)`** — the stock widget is a white puck with a Holo-blue arrow, wrong in both schemes. Note it reads `colorPrimary` from `androidx.appcompat.R.attr` but the `colorSurfaceContainer*` roles from `com.google.android.material.R.attr`; they live in different R classes and swapping them doesn't compile.

| Screen | id | Refresh action | Spinner stopped in |
|---|---|---|---|
| Автопарк | `homeSwipe` | `loadVehicles()` | `stopVehicleRefreshIndicators()` |
| Поддръжка | `maintSwipe` | `refreshMaintenanceTypes()` — clears the session cache, then refetches | `deliverTypes(...)` |
| Профил | `profileSwipe` | `loadVehicles()` (fleet stats derive from it; name/email/avatar are login-cached and **cannot** refresh here) | `stopVehicleRefreshIndicators()` |
| Vehicle detail | `detailRoot` | `refreshFromServer()` — re-runs the photo-name + schedule fetches | `renderMaintenance(...)`, which every fetch path funnels into |

On the detail screen the `SwipeRefreshLayout` **is** `#detailRoot` (the `ScrollView` is now `#detailScroll`) so the existing window-inset padding lands on the outer view and keeps the spinner clear of the status bar. Each swipe ref is nulled by its tab's `clear*Refs()` so a late callback can't touch a detached layout.

### Автопарк overview (home dashboard)
The Home tab leads with `#homeOverviewCard` (M3 tonal card), filled by `MainActivity.refreshOverview()`. It replaced the old single warning banner because that banner had become a cramped dumping ground once documents were added to it.

- **Two stat tiles:** vehicle count, and **„За внимание“** = the number of *vehicles* (not alerts) with any DUE/OVERDUE in either category, so a car with two problems counts once. The attention value is neutral at 0, amber if only due-soon, red if anything is overdue.
- **Alerts split into two category rows — Обслужване and Документи** — each shown only when it has something, each tinted by its <em>own</em> worst severity via the `status_*_text` colours (on-background flavour, not the badge fills). An „Всичко е наред“ row shows when both are clear.
- The card is **hidden when the fleet is empty** (the empty-state illustration shows instead) — toggled in `refreshHomeSummary()` alongside the recycler/empty state.
- Same data source as the badges and the worker: `vehicleStatuses` (service) + `vehicleDocStatuses` (documents). `refreshOverview()` is called wherever either map changes, so the card, the row badges and the notification can never disagree.

### Service reminders (Автопарк tab)
After each `loadVehicles()`, `loadMaintenanceStatuses()` fires **one `GET /vehicles/maintenance?id=` per vehicle** (each retried up to `STATUS_MAX_ATTEMPTS` on the flaky server; a vehicle that still fails is left unbadged rather than blocking the others) and derives a per-vehicle **worst-case status** via `util/MaintenanceStatus.worst(...)`. Results feed two UI elements on the Home tab: a colored **status pill** on each list row (`VehicleAdapter.setStatuses`) and a fleet **reminder banner** (`homeReminderBanner` in `home_content.xml`) that tallies vehicles with overdue / due-soon service (`refreshReminderBanner()`). Statuses live in a `Map<String, MaintenanceStatus> vehicleStatuses` (id → status), mutated only on the main thread; a `statusLoadGeneration` counter discards callbacks from a superseded reload. Switching back to the tab re-applies the cached map without refetching. `util/MaintenanceStatus` (enum OK/DUE/OVERDUE, ordered by severity) and `MaintenanceItem.listFromJson(...)` are the shared source of truth for both this and `VehicleDetailActivity`'s schedule cards.

### Assisted document check (`VinCheckActivity`) — ГТП only
The **ГТП** card's „Провери“ button opens RTA's check page **inside the app** in a WebView, rather than deep-linking to the browser. The point is to get most of the way to an automatic check without crossing the line a captcha draws. `VinCheckActivity` is still written **site-agnostically** — the caller passes the URL, the host to inject on, the value to prefill/copy, the CSS selectors for the field, and the labels — but it has exactly **one caller**: `openInspectionCheck()`.

- **ГТП → RTA** (`public-eis.rta.government.bg`, Angular SPA, Google reCAPTCHA), fills the VIN field, saves to `inspectionValidTo` via `vinCheckLauncher`.
- **ГО does NOT use this screen — it opens the browser (`openExternal`), and that is the final answer (2026-08-19).** See **Why ГО is a link-out** below before touching it.

- **The human solves the reCAPTCHA; the app never touches the token.** RTA's own Angular app makes the API call with a real, Google-solved token; this screen only *reads the rendered result*. It does not forge, reuse, or intercept the token — that would be circumventing the control (RTA's `siteverify` is misconfigured, but a broken lock is still a lock; see `docs/rta-access-request-email.md` for the authorised-access route that would replace all of this).
- **Nothing is saved silently.** A scraped date is only *offered*: the result bar appears, the user confirms it against what's on screen, and `VehicleComplianceActivity` persists it through the same `persist(...)` path as a hand-picked date. If RTA changes their DOM the scrape finds nothing, the bar never shows, and the user falls back to reading the date + „+1 година“. **The failure mode is "no help", never "wrong date".**
- **VIN prefill is best-effort; clipboard is the reliable fallback.** The injected JS tries several selectors for the VIN field and dispatches `input`/`change` so Angular's form control notices; the VIN is also copied to the clipboard so a paste always works if the selectors miss.
- **The injected script runs only on `public-eis.rta.government.bg`** (`onPageFinished` host check), never in a reCAPTCHA frame or a redirect target. The `MvBridge` JS interface exposes one annotated method (`onDatesFound`) and its input is treated as untrusted — which is fine precisely because it only ever populates a confirm dialog.
- **The `; wv` UA strip is scoped to the RTA (reCAPTCHA) host only.** Google reCAPTCHA refuses to run under the WebView UA token. **Keep the `allowedHost.contains("rta.government.bg")` guard even though RTA is now the only caller** — the same strip once gave the Guarantee Fund a black screen (an unusual UA can trip a CMS/WAF), so it must never be applied blindly to whatever page is wired up next. Other hardening, none of it host-specific: an explicit white WebView background (the surface is black until first paint), `MIXED_CONTENT_COMPATIBILITY_MODE`, and a `WebChromeClient`.
- **A failed load is visible, not blank.** `onReceivedError` (main frame only — a dead tracker iframe is not a failed page) and a 20 s `loadWatchdog` raise `#vcErrorBar` with *Презареди* / *Отвори в браузър*; there's also a `#btnReload` in the header and `#btnOpenBrowser` as the always-available escape hatch. The watchdog does **not** cancel the load, it only offers the exits. `reload()` calls `loadUrl(url)`, **not** `WebView.reload()`, so a result page reached by POST isn't re-submitted. `onConsoleMessage` logs the page's own JS errors to logcat and `setWebContentsDebuggingEnabled` is on for debuggable builds, so `chrome://inspect` works — that combination is the only practical way to diagnose "the page just doesn't come up".
- Extraction floats candidates whose label contains „валид / до / след / преглед“ to the top, so the pre-selected date is the useful one; several distinct dates → a single-choice dialog. This is the most brittle code in the app on purpose kept thin and heavily guarded.
- With **no VIN stored** the page can't work, so `openInspectionCheck()` falls back to opening it in the browser rather than launching an empty WebView.

#### Why ГО is a link-out and must stay one
The Guarantee Fund's page was hosted in this same WebView and **loaded only intermittently**, while RTA's never failed once. Two real defects on the Fund's side were found and worked around, and it *still* failed on device — so ГО now opens in the user's own browser (a full Chrome, none of the WebView's constraints) with the VIN, or the plate when there is no VIN, on the clipboard. Same treatment as the vignette-purchase link. The date comes back via the picker or the „+1 година“ renewal row.

**Do not re-introduce the WebView for ГО** without evidence their page changed. What was already tried and removed, so it isn't tried again:
1. **Render-blocking third-party assets.** Their page has a `fonts.googleapis.com` stylesheet in `<head>` and a blocking `code.jquery.com/ui/1.12.1/jquery-ui.js` at the end of `<body>`, plus `googletagmanager`. One slow host ⇒ the WebView paints nothing. A `shouldInterceptRequest` that answered those hosts with an empty body did not fix it.
2. **An ALTCHA init race in their own JS.** They configure the widget from a `window.load` handler whose first statement is `document.querySelector('[id^="altcha_checkbox_"]').setAttribute(...)`; that checkbox is rendered by the widget's own **async `type="module"`** bundle, so on a slower device it doesn't exist yet, the handler throws, `configure()` is never reached, and the widget has no challenge. Nothing in their code retries. A repair script that called their own `configure(...)` with a challenge fetched from their own `/ajax/altchagenchlange.php` did not fix it either.

Both workarounds were deleted along with the ГО launcher, `HOST_INSURANCE`, and the `vc_*_insurance` strings — `VinCheckActivity` carries no Guarantee Fund code any more. Note the diagnosis above was read out of their page source, never reproduced on device; whatever remains is inside their page and not reachable from our side. `VinCheckActivity` itself stays: ГТП still uses it.

### Renewing a declared document
An expired ГТП card used to be a dead end: it stayed red after the user had actually renewed, which trains people to ignore the badge. `#cmpRenewRow` on `item_compliance_card.xml` fixes that.

- It **asks a question** („Мина ли прегледът?“ / „Подновихте ли полицата?“) rather than announcing a state — at that moment the user is the only one who knows whether the inspection happened, and a tap is a cheaper answer than a date picker.
- Shown **only for DUE/OVERDUE**. On a healthy document it is clutter; with no date at all there is nothing to extend and the picker is the right tool. There is no „Не още“ button on purpose — not tapping already means that, and a dismissal would need state to remember.
- **`ComplianceStatus.plusOneYear` extends from whichever is later, the old expiry or today.** Both halves matter: renewing early must not forfeit the days left, and renewing late (the common case) must not add a year to a long-gone expiry and land back in the past. Unit-tested both ways in `ComplianceStatusTest`.
- **Never offered for an instalment.** The ГО card's row is driven by the *policy* status, not `worst(...)`: instalments are quarterly or monthly, so „+1 година“ would be simply wrong. An instalment-only problem falls through to „Промени дата“.
- The success toast **names the new date** (`cmp_renewed`), because the user never typed it and would otherwise have to go looking to see what the app decided.
- Not built: a „+1 година“ action on the notification itself. It needs a `BroadcastReceiver` doing a network write with no UI to report failure into; the notification already deep-links to this card, so renewing from a notification is two taps.
- **Sticker OCR was considered and rejected.** The ГТП sticker encodes its expiry as a *perforation* through a pre-printed year/month, not as text — so text recognition reads every year on the sticker and cannot tell which was punched. Reading it would need a custom vision pipeline (find the ellipse, rectify, locate the hole, map to a month sector) through windscreen glare, and its failure mode is a silently wrong reminder date. Don't revisit it; this renewal flow is the answer to the same problem.

### Document reminders (badges, banner, notifications)
Document validity feeds the same three surfaces service reminders do, but stays a **separate track end to end**. The reason is one sentence: an overdue oil change and an expired vignette differ in both urgency and remedy, and one signal that covered both could tell the user neither.

- **A second row badge, not a merged one.** `item_vehicle.xml` stacks `#txtVehicleStatus` (service) over `#txtVehicleDocStatus` (documents, marked by `ic_shield_small` — a 14dp twin of `ic_shield`, because `android:drawableStart` renders a vector at its intrinsic size and the 24dp original dwarfs an 11sp pill). Fed by `VehicleAdapter.setDocStatuses`.
- **The document badge has no OK state.** `ComplianceStatus.OK` and "unknown" both render as nothing. Two of the three dates are user-declared, so a reassuring green badge would be a claim the app cannot back — absence means "nothing to flag", never "this car is road-legal". Same rule as the detail screen's `#detailDocWarning`.
- **Alerts live in the Автопарк overview card, split by category** (see **Автопарк overview** below) — they are tallied separately, never merged, because an oil change and an expired vignette are different problems. (The old single `homeReminderBanner` was replaced by that card; `reminder_doc_*` plurals are retained for the background *notification*, which is a different surface.)
- **`MainActivity.loadDocumentStatuses()` is two-phase.** The ГТП/ГО dates arrive with `GET /vehicles`, so those badges are applied **synchronously** and land with the list; only the vignette needs `GET /vehicles/vignette?id=` per vehicle (`fetchVignetteStatus`, retried via `STATUS_MAX_ATTEMPTS`), and it merely *upgrades* a badge that is already right for everything else. So a failed vignette check still leaves the declared expiries visible. `applyDocStatus` recomputes the declared half from the `Vehicle` each time rather than caching it, which is what makes it safe to call twice per vehicle.
- **`docLoadGeneration` is its own counter**, not shared with `statusLoadGeneration`: the two loads finish independently and one counter would let either cancel the other's callbacks.
- **Own notification channel and id** (`document_reminders` / 2002) so muting service nags doesn't also mute the ones that carry a fine, and so the two never overwrite each other in the shade.
- **Own suppression signature** (`KEY_DOC_SIGNATURE` / `KEY_DOC_NOTIFIED_AT`). **Do not fold documents into the service signature** — a vignette changing state would reset the 7-day quiet period for service reminders, re-notifying the user about an oil change they had already dismissed for a reason that has nothing to do with it.
- **The document notification is actionable**: with exactly one vehicle affected the tap lands on that car's `VehicleComplianceActivity` via `TaskStackBuilder` (MainActivity synthesised underneath, so Back behaves), where a vignette can be bought or a date fixed. More than one → `MainActivity`.
- In the worker, a failed vignette fetch returns `null` and `ofVignette(null)` yields no status — so "we couldn't check the vignette" never erases "your ГТП expired last week", and never invents an overdue either.
- **`notifyDue` and `notifyDocumentsDue` duplicate their permission guard on purpose.** Extracting it into a helper fails `lintDebug` with `MissingPermission`: lint only recognises a `checkSelfPermission` guard it can see dominating the `notify()` call in the same method. It was tried; the duplication is the price. (`areNotificationsEnabled()` alone is not accepted as a permission check either — both are needed.)

### Shareable history link (QR)
`ShareHistoryActivity` shows a scannable link to one vehicle's **public** history page, reached from the third item of the detail screen's export dialog. **Blocked on the backend** — `POST /vehicles/share`, `POST /vehicles/share/revoke` and the public `GET /s/<token>` page (see the endpoint list) do not exist yet, so the screen currently fails with "Линкът не можа да бъде създаден".

- **The link is minted server-side, never built in the client.** A URL the app assembles would have to contain the vehicle id, which makes every car in the database enumerable. The token is opaque, revocable and expiring; the client only displays what it's handed.
- **The reader is a browser, not this app** — the buyer has nothing installed — so `/s/<token>` must serve HTML. That's the one genuinely new capability required of the C++ server, which so far only emits JSON.
- **QR encoding is ZXing `core` only** (`util/QrCodes`), not `zxing-android-embedded`: the app encodes codes and never scans them, so nothing camera-related is needed.
- **The code is always black-on-white and sits on a hardcoded white card in both themes.** Scanners expect a dark code on a light quiet zone; inverting it for dark mode reads slowly or not at all. Same reasoning as the PDF's hardcoded colours.
- `onResume` pushes `screenBrightness` to 1.0 — a dim screen is the usual reason a QR won't scan, and the user can't fix that from this screen. The system restores it when the Activity goes away.
- Revoke is behind a confirm dialog and **finishes the Activity on success**, so a dead link isn't left on screen still looking scannable.

### Service-history PDF export
`util/ServiceHistoryPdf` renders a vehicle's history to a PDF; `VehicleDetailActivity`'s header **share** button (`#btnExport`) fetches the data and opens a share sheet.

- **Reads `GET /vehicles/maintenance/history`, not `/vehicles/maintenance`.** The latter is latest-per-type, which would produce a "history" of one line per service type. This is the only caller of the history route.
- **Two sections, answering different questions:** a summary of the latest record per type ("when was the timing belt last done?") and the full chronological log ("was this car looked after?"). The summary is derived in the renderer from the same payload — *not* fetched from the latest-per-type endpoint — so the whole document is one consistent snapshot. It keys on `typeId`, falling back to `name` when the server omits it.
- **Colours are hardcoded, not `?attr/` roles.** A PDF is printed and read outside the app; resolving theme attributes would export a navy page whenever the user is in dark mode. This is the one place in the codebase where raw hex is correct.
- Plain `android.graphics.pdf.PdfDocument`, no library. A4 at **72dpi (595×842)** — the unit `PdfDocument` works in.
- **Pagination:** `ensureSpace(n)` returns false after it breaks a page, so the caller can redraw what the break invalidated — `drawRow` uses this to repeat the table column heads. Row height (including wrapped notes) is measured *before* drawing so a row moves to the next page whole rather than splitting across the break.
- **Rendering happens on OkHttp's callback thread**, not the main thread, then hops to the UI thread to deliver. `exportInFlight` + disabling the button stop a double-tap producing two files.
- **Two destinations, chosen up front.** Tapping export opens a dialog — *Запази в устройството* / *Сподели* — and the answer is taken **before** the fetch, so the user isn't left waiting on a download and then asked a question. `saveAfterExport` carries the choice through to `finishExport`.
- **Saving uses the Storage Access Framework** (`ActivityResultContracts.CreateDocument`), not a direct write to Downloads. SAF needs **no storage permission on any API level**; `MediaStore.Downloads` is only permission-free from API 29, and `minSdk` here is 24, so that route would have needed a `WRITE_EXTERNAL_STORAGE` path as well. The rendered file is held in `pendingExportFile` while the picker is open (null it out when the user backs out), and the save confirmation is a Snackbar with an **Отвори** action — a bare toast leaves the user hunting for where the file went.
- **Sharing goes through `FileProvider`** (authority `${applicationId}.fileprovider`, `res/xml/file_paths.xml` → `cacheDir/exports`). A `file://` URI throws `FileUriExposedException` from API 24 on, which is this app's `minSdk`.

### Document photos on maintenance records
A service record can carry one photo of its paperwork — a receipt, an invoice, a protocol — picked on `AddMaintenanceActivity` and viewed full-screen from the schedule cards on `VehicleDetailActivity`. `util/MaintenanceDocuments` + `DocumentViewerActivity` + `view/ZoomableImageView`. Backend contract is written up in `docs/backend-maintenance-documents-task.md`.

- **This is a third image transport and it deliberately differs from `VehicleImages`.** Vehicle photos are base64 inside JSON; documents are **raw bytes** with a real `Content-Type`/`Content-Length`. base64 is +33% on mobile data for the largest payloads the app moves, it makes the client hold the encoded string *and* the decoded bitmap at once, and a raw body streams and gives working `ETag`/`304`. Don't "unify" the two by pushing documents back through base64.
- **The list endpoints carry a `documentId`, never the bytes.** `GET /vehicles/maintenance` and `…/history` gained one field; a vehicle's history is tens of records, so embedding images would multiply one photo by the whole history in a single response. Bytes come from `GET /vehicles/maintenance/document?id=` one at a time, on tap. `MaintenanceItem.documentId` is `""` for both "no document" and an older server build, so display sites just hide the button.
- **Upload is a second request, after the record is saved, and the record is never rolled back if it fails.** `POST /vehicles/maintenance/add` now returns `{"id":…}`; `MaintenanceDocuments.upload` then POSTs `multipart/form-data` to `/vehicles/maintenance/document`. A multi-megabyte upload from a phone dies to a tunnel or a cell handover regardless of server health, and that must not cost the user the service record they just typed — `finishSave(documentFailed)` returns `RESULT_OK` either way and only changes the message (`am_saved_doc_failed`). A missing `id` in the add response degrades the same way: record saved, photo skipped, user told.
- **The document is JPEG at 2048px; the vehicle photo is lossless WebP/PNG at 1024px.** Both choices are deliberate and opposite. A document must stay *legible* — 1024px turns 8pt print to mush — but it's flat paper with no alpha, so JPEG q85 lands a readable scan in a few hundred KB. A vehicle photo may be a transparent PNG, which JPEG would flatten onto a solid background.
- **`util/PickedImages` is now the single decode path for both pickers**, which is the whole reason it exists: the EXIF-orientation fix is exactly the kind of thing that gets made in one screen and forgotten in the other. It also downsamples via `inJustDecodeBounds` + `inSampleSize` before decoding — a 12MP photo is ~48MB as ARGB_8888, and the old decode-then-scale order risked OOM before the scale ran.
- **The viewer takes only the `documentId`, never a bitmap** — a real photo would blow the ~1MB Binder transaction limit. `MaintenanceDocuments` caches decoded documents by id, and a document is immutable once uploaded (a replacement gets a new id), so a cache hit can never be stale and re-opening skips the spinner entirely.
- **`ZoomableImageView` is hand-written, not a library.** Pinch/drag/double-tap is a `Matrix`, a `ScaleGestureDetector` and a bounds clamp; the app needs it on one screen. Note it must extend `AppCompatImageView` — `lintDebug` fails with `AppCompatCustomView` otherwise. `clampToBounds` centres an axis smaller than the view as well as pinning a larger one; without the centring half, zooming out leaves the image jammed in whichever corner the pinch ended on.
- **The viewer's backdrop (`@color/document_backdrop`) is the same dark neutral in both themes, not a `?attr/` role.** A scanned receipt is off-white paper; on a light surface its edges vanish and the user can't tell where the document stops. Same class of decision as the PDF export's hardcoded colours.
- **A failed fetch shows `#dvError`, never an empty frame** — a blank viewer reads as "the document is empty" rather than "it didn't load". Same rule as the document badge having no OK state.
- **Documents are excluded from the public share page** (`GET /s/<token>`) and that is a hard rule, not an oversight: a photographed invoice routinely carries the owner's name, address, phone and signature, and that page's whole constraint is "no owner PII". The user attached a receipt to track a service, not to publish it. Any "share documents too" option needs its own explicit per-share opt-in.
- Not built yet: embedding documents in the PDF export (the owner's own export, so it would be legitimate), and more than one document per record — the server table is keyed by `record_id` so N is possible, but the UI ships with one and the read path returns the newest.

### Oil advisor (препоръка за масло)
`OilRecommendationActivity`, reached from the tappable `#cardOilAdvisor` row on the Поддръжка tab (a row, not a second FAB — the tab's FAB owns the primary *write* action and this is a lookup). Models: `model/EngineOption` + `model/OilRecommendation`. Backend contract: `docs/backend-oil-recommendation-task.md` — **both routes are unimplemented server-side**, so the screen currently shows its two error states.

- **Cars only.** The vehicle picker is filtered by `VehicleType.supportsOilAdvisor()` at both call sites, and the picker's helper text (`oil_cars_only`) says so; a fleet with no car gets `oil_no_cars` instead of an empty form. Motorcycle oil is a different product (wet clutch, JASO MA) and a truck's different again — see **Vehicle types**. Adding those means a separate table and route, never a `vehicleType` filter on `/oil/recommend`.
- **The lookup key is the engine code, not make/model/year, and that is the whole design.** One model year ships several engines with different oil requirements (a Golf VI is a 1.4 TSI *and* a 2.0 TDI); the requirement follows the engine. The vehicle picker exists to prefill the fuel type and to remember the choice — it does **not** identify the engine. This is also the conclusion of the earlier "no usable oil API" investigation: nothing free resolves VIN/model to an engine code for the European used-car park, so a curated server table is the answer.
- **The approvals are the answer; the viscosity is just what's on the bottle.** `specs` (VW 507 00, MB 229.51, BMW LL-04 …) gets its own labelled block because a 5W-30 without the right approval still destroys a DPF. `products` is deliberately the quietest part of the card — a brand is interchangeable, an approval is not.
- **Read-only screen.** No save button, no `RESULT_OK` contract, no `SwipeRefreshLayout` (re-asking is one tap on `#btnRecommend`). Nothing here writes to the server.
- **The engine field stays typeable and a failed catalog fetch never disables the form.** `GET /oil/engines` seeds the dropdown and `applyEngineItems()` floats the engines fitted to the selected vehicle's make to the top; a code that isn't in the 20-row table yet must still be sendable, so the field is an editable autocomplete (text `inputType`, not the usual `inputType="none"`) and a failed fetch only raises `#oilEnginesError`. `engineCodeToSend()` therefore accepts a picked label *or* a hand-typed code, pulling the code out of the trailing parentheses.
- **The picked engine is resolved by label, not by adapter position** (`enginesByLabel`): the autocomplete filters as the user types, so a click position refers to the filtered adapter, not to our list. Note `setSimpleItems` replaces the adapter and clears the text, so `applyEngineItems()` puts the typed text back — otherwise switching vehicle would silently wipe it.
- **No hardcoded client fallback catalog**, unlike `/maintenance/types`. An oil approval the app invented would be indistinguishable from one the server vouches for, and the failure mode has to be "no help", never "wrong spec".
- **404 is a real answer** ("the catalog doesn't know this engine") and is not retried — asking three times can't add a row. IO failures and truncated bodies are retried up to `OIL_MAX_ATTEMPTS`, same as every other idempotent GET. An unusable 200 (`!isUsable()`) is reported as no-data rather than rendered as a card with blank fields.
- **`fuelType` is a tiebreaker the server must not treat as a filter**, because it's prefilled from the user-typed `Vehicle.fuelType`. `lpg` falls back to the petrol row plus a caveat — an LPG conversion *is* a petrol engine, and conversions are a large share of the local petrol park. **Electric disables the form** with an explanatory message instead of asking for a recommendation that cannot exist.
- Missing capacity/interval are hidden, never printed as 0 — same rule as `MaintenanceItem.cost`.
- **The engine choice is remembered per vehicle in a separate `"oil"` prefs file** (not `"auth"`, which logout clears), and only after an answer the catalog recognised, so a rejected typo isn't what greets the user next time. The proper home is an `engineCode` column on the vehicle; that's written up in the task doc and would make this cache deletable.
- The footnote is load-bearing, same class as the compliance screen's provenance strings: it says the recommendation is derived from the engine code and that the binding requirement is the manufacturer's approval in the owner's manual. Don't genericise it away.

### Biometric unlock
`util/BiometricLock` (AndroidX **biometric**, catalog entry `biometric`) puts an optional fingerprint/face gate in front of the **auto-login shortcut** — `LoginActivity` walking straight into `MainActivity` because the `"auth"` prefs hold a username. **No backend involvement at all.**

- **It is not encryption.** The Bearer token still sits in plain SharedPreferences; this stops a person holding the unlocked phone, not someone reading the app's data directory. `EncryptedSharedPreferences` would be the next step if that matters.
- **The preference lives in a separate `"settings"` prefs file**, not `"auth"` — logout clears `"auth"`, which would silently switch the lock back off.
- **Authenticator is `BIOMETRIC_WEAK` with the password form as the negative button**, deliberately *not* `DEVICE_CREDENTIAL`: mixing device credential into the authenticators is unsupported on API 28–29 and would need version-specific handling, while "log in with your password" is a fallback already on screen and works on every API level.
- **Unavailable biometrics ⇒ password login, not a free pass.** If the lock is on but hardware/enrolment is gone, `LoginActivity` leaves the user on the form rather than honouring the saved session — they can always sign in normally, so this can't lock anyone out.
- `onAuthenticationFailed` (a finger that didn't match) is intentionally **not** overridden — the system prompt stays up and lets the user retry. Only `onAuthenticationError` ends the flow, and a deliberate dismissal (`ERROR_NEGATIVE_BUTTON`/`USER_CANCELED`/`CANCELED`) reports a null message so no pointless toast appears.
- **Enabling the switch prompts first and only persists on success** — enabling a lock that can't be opened would strand the user next launch. Disabling doesn't prompt: whoever sees that screen is already past the gate. The programmatic revert is guarded by `revertingBiometricSwitch`, or it would re-enter the listener's "off" branch and stack a second toast.

### Service reminder notifications (background)
`work/ServiceReminders` + `work/ServiceReminderWorker` (AndroidX **WorkManager**, in the version catalog as `work-runtime`) run a **daily** check for vehicles whose service is due/overdue and post a notification. **No new endpoint** — the worker re-uses `GET /vehicles`, `GET /vehicles/maintenance?id=`, `MaintenanceItem.listFromJson` and `MaintenanceStatus.worst`, so a notification and an Автопарк badge can never disagree. `Vehicle.fromJson(...)` was moved out of `MainActivity` into the model for exactly this reason; don't re-add a second parser.

- **Requests are synchronous** (`execute()`, not `enqueue()`): a `Worker` is already off the main thread, and the Activities' callback style would let `doWork()` return before the responses landed.
- **Failure handling mirrors the UI's rule.** A failed `GET /vehicles` returns `Result.retry()` — "unknown" must not be reported as "nothing due". A single vehicle's failed maintenance fetch is skipped so it can't hide the others.
- **Repeat suppression:** a sorted `id:STATUS` signature is stored in the `"reminders"` prefs. The same fleet in the same states won't re-notify until `REMIND_AGAIN_MS` (7 days); any change notifies at once. When nothing is outstanding the signature is cleared, so the next problem isn't swallowed as "same as last time".
- `schedule()` uses `ExistingPeriodicWorkPolicy.KEEP`, so calling it from every `MainActivity.onCreate` doesn't push the next run back a day — **but if the interval is ever changed this must become `UPDATE`**, since KEEP leaves the enqueued job on the old period.
- **Logout calls `ServiceReminders.cancel(...)`**, which also clears the `"reminders"` prefs — otherwise the job keeps waking for a signed-out user and the next user is silenced by the previous one's signature.
- `POST_NOTIFICATIONS` is runtime-requested on API 33+ (`MainActivity.requestNotificationPermissionIfNeeded`). The result is ignored on purpose: the job is scheduled either way and simply posts nothing while refused. `notifyDue` re-checks the permission *and* `areNotificationsEnabled()` — the explicit `checkSelfPermission` is required, since lint doesn't accept `areNotificationsEnabled()` as a permission check.
- Note `TextUtils.join`, not `String.join` — the latter is API 26 and `minSdk` is 24.

### Theming (colors, light/dark)
The app has **one** theme definition — `values/themes.xml` (`Base.Theme.MaintenanceApp`, parent `Theme.Material3.DayNight.NoActionBar`) — that maps every Material 3 color role to an `@color/scheme_*` name. Those names are defined **twice**: `values/colors.xml` (light: white/off-white surfaces, deep azure `#0E7490` primary) and `values-night/colors.xml` (dark: navy `#0B1220` page, `#151E30` cards, cyan `#22D3EE` primary). Android resolves per-mode, so the single style block skins both.

- **`values-night/themes.xml` is deliberately empty.** Styles do *not* merge across resource qualifiers — redefining `Base.Theme.MaintenanceApp` there would replace the light definition wholesale and force the whole role mapping to be maintained twice. **To change dark colors, edit `values-night/colors.xml`.**
- Layouts must reference `?attr/…` roles (`colorSurface`, `colorSurfaceContainer`, `colorOnSurfaceVariant`, `colorOutlineVariant`, …), never raw hex. Page background is `?attr/colorSurface`; cards are `?attr/colorSurfaceContainer` with a 1dp `?attr/colorOutlineVariant` stroke and `cardElevation="0dp"` (M3 tonal elevation, not shadows).
- **Status colors come in two flavours and they are not interchangeable.** `status_ok/due/overdue` are **fills** — used as a solid badge background with white text on top (`VehicleAdapter`, `VehicleDetailActivity` via `MaintenanceStatus.colorRes`), so they stay dark in both modes. `status_*_text` are the same three states used as **text/icon tint directly on the page background** (the Автопарк reminder banner in `MainActivity.refreshReminderBanner()`); these invert to light tints at night. Using a fill color as text on navy is unreadable — pick the right one.
- `window_light_system_bars` (`values(-night)/bools.xml`) drives `windowLightStatusBar`/`windowLightNavigationBar`, since edge-to-edge means only system-bar *icon* contrast is ours to set.
- Bottom nav is styled theme-wide via `bottomNavigationStyle` → `Widget.App.BottomNav`, whose active indicator is re-pointed at `colorPrimaryContainer` (the stock M3 default is the secondary container) with `color/bottom_nav_item.xml` as the icon/label selector. `activity_main.xml` needs no changes.
- **Icons:** all `ic_*.xml` vectors use `fillColor="#FF000000"` and rely on a tint at the use site — an untinted one is invisible on navy. Exceptions are intentional: `ic_avatar_placeholder` and the four `*_placeholder` PNGs sit in ImageViews whose image is later *replaced* by a real photo, so those views must not carry `android:tint` (it would recolor the photo); the placeholder's neutral color is baked in instead. No `@android:drawable/*` framework icons remain in layouts — they don't adapt to the dark scheme.

### Session/auth state
Auth is a lightweight convention, not a framework: the `"auth"` SharedPreferences file with a `username` key is the single source of truth for "logged in." Any screen that gates on login or logs out reads/writes this same file (`getSharedPreferences("auth", MODE_PRIVATE)`). Profile fields are also cached here from the login response.

### Networking
HTTP goes through **OkHttp** directly (no Retrofit/repository layer). Calls are async via `client.newCall(...).enqueue(...)`, and every UI update from a callback is wrapped in `runOnUiThread(...)`.

- **Auth (Bearer token):** login returns a `token`, saved in the `"auth"` prefs. Every Activity gets its OkHttp client from **`util/ApiClient.get(ctx)`** (a process-wide singleton) instead of `new OkHttpClient()`; its interceptor reads that token and stamps `Authorization: Bearer <token>` on every outgoing request (skipped when no token is stored, so login itself is unaffected). Because the server derives the user from the token, requests **do not send a username** — neither as a query param nor in a body. Assign the client in `onCreate` (`client = ApiClient.get(this)`), **not** as a field initializer: the Activity's context isn't attached yet at construction time. Logout clears the `"auth"` prefs, which drops the token too.
- **Backend base:** `http://92.5.55.85:27778` (a hand-rolled C++ server). It's plain **HTTP**, so `res/xml/network_security_config.xml` whitelists cleartext to that IP and the manifest references it. Endpoint URLs are hardcoded as constants in the Activities.
- **Endpoints in use:**
  - `POST /users/login` — body `{username,password}`; returns the profile JSON incl. the Bearer `token`. One of only two requests that carry no `Authorization` header.
  - `POST /users/register` — **not implemented server-side yet.** Body `{"username","password","fullName","email"}` (email already lower-cased by the client). Requires **case-insensitive unique** indexes on `username` and `email` — the client's "not retried" rule assumes a duplicate can never become a second row. On a collision return **409** with `{"error":"username_taken"}` or `{"error":"email_taken"}`, since the status alone can't tell the client which field to mark. 400 for validation failures; re-validate everything server-side (the username charset/length rules are UI convenience, not enforcement). Adding `imageBase64` here means N photos in one response — weigh that against the truncation bug before doing it.

The client reads both and prefers the base64; when neither is present it leaves whatever's on screen. Called by `VehicleDetailActivity.fetchPhoto` on open and on pull-to-refresh. **The base64 body is what kept getting truncated for large images** — the client retries a short read (`IMAGE_MAX_ATTEMPTS`) and degrades gracefully on a mid-payload cut, but the real fix is server-side.

Omit `cost` (or send `null`) when the column is `NULL`; the client reads either as "not recorded" and shows nothing, and **never as 0**. **Each item is the _latest_ record per service type, not a raw record** — the C++ side uses `SELECT DISTINCT ON (maintenance_type_id) ... Also carries **`documentId`** (absent/null = no document photo) — the *id only*, never the image bytes. (mileage in km; `lastChangeDate`/`notes` present only when set). No records → `{"items":[]}`. Consumed by `VehicleDetailActivity` (implemented server-side in `VehiclesCmd`/`RequestServer`). Status (OK / Due soon / Overdue) and the progress bar are computed client-side from `nextChangeMileage - currentMileage` vs. the `next - last` interval.

Being server-side is also what lets that breakage be fixed by a deploy instead of an app update.

Returns `{"types":[{"name","defaultIntervalKm","description"?}, ...]}` (catalog for the Поддръжка grid + add-service dropdown). `description` is optional; when non-empty the tab shows an info (ⓘ) button that reveals it as a yellow warning (e.g. timing-belt caveats). **Gotcha:** an empty/unseeded `maintenance_types` table returns `{"types":[]}`, which the client treats as a failure and silently swaps in its hardcoded Bulgarian fallback — so a broken catalog looks identical to a working one. Reject a negative `cost` with 400.
- **Images:** **two transports coexist**, and every display site goes through **`util/VehicleImages.apply(ctx, imageView, base64, name, cacheKey)`**, which tries them in a fixed order: **(1)** `imageBase64` — the photo itself, uploaded by `POST /vehicles/add` and stored in the DB; **(2)** `imageName` — a bare name (lowercase, no extension) resolved to a **drawable bundled in the APK** via `Resources.getIdentifier(...)`, for seed data whose photos ship with the app; **(3)** the **placeholder for the vehicle's own type** (`VehicleType.placeholderRes` → `car_placeholder` / `motorcycle_placeholder` / `van_placeholder` / `truck_placeholder`, all PNGs), so a bike with no photo doesn't sit in the Автопарк list wearing a car. `apply`/`resolve` therefore take a `VehicleType`; a null one reads as `DEFAULT`. Layouts' `android:src` names `car_placeholder` only as the pre-bind default — the real choice is made in code. These four are deliberately **not** theme-aware and **not** tinted at the use site, same rule as `ic_avatar_placeholder`: they sit in ImageViews whose image is later *replaced* by a real photo, so an `android:tint` there would recolour the photo. Base64 wins when non-empty, so a user-uploaded photo overrides a bundled one.
  - **`res/drawable/` cannot be written at runtime** — AAPT compiles it into the APK at build time. So the name transport can only ever refer to photos that shipped with the app; a photo the user picks *has* to travel as base64. (Turning a picked photo into a bundled drawable means adding the file to the source tree and rebuilding — `res/drawable/` is flat, no subfolders, names `[a-z0-9_]`.)
  - `AddVehicleActivity` downscales the pick to ≤`MAX_IMAGE_DIMEN` (1024px longest side) and encodes it **lossless WebP** (API 30+) or **PNG** — not JPEG, which has no alpha and would flatten transparent PNGs onto a solid background.
  - **EXIF orientation is baked into the pixels** by `applyExifOrientation(uri, bitmap)` (AndroidX `exifinterface`, catalog entry `exifinterface`). A camera stores a portrait shot as landscape pixels plus an `Orientation` tag; galleries honour it, `BitmapFactory` does not — so portrait photos uploaded **sideways** while landscape ones (tag = 1) looked fine. That asymmetry is the tell. There is no "preserve the metadata" option: the re-encode to WebP/PNG carries no EXIF, so the rotation is either in the pixel data or lost. This is also why `VehicleImages` needs no matching fix — everything downstream decodes an already-upright image. Reads EXIF from a **second** `openInputStream` (the first is consumed by the decode, and a `ContentResolver` stream isn't reliably rewindable), applies **after** `scaleDown` (which caps the longest side, unchanged by a 90° turn, so the matrix works on fewer pixels), covers the mirrored orientations too, and returns the bitmap untouched on any failure.
  - Flow: `VehicleDetailActivity` shows whatever the list row already had, then `fetchPhoto` calls `GET /vehicles/image?id=` and re-applies with whichever field came back. List rows (`VehicleAdapter`) render `Vehicle.imageBase64`/`imageName` only if `GET /vehicles` includes them — rows never fetch per-id, so otherwise they show the placeholder.
  - Decoded bitmaps are held in a static `LruCache` (¹⁄₈ of heap) keyed by **vehicle id**, because `RecyclerView` re-binds on every scroll and base64-decoding a ~1MP image per bind janks the list. `VehicleImages.evict(id)` drops an entry — called before the detail screen applies a freshly fetched (possibly larger) rendition, and after a vehicle delete so a recycled id can't inherit the old photo.
  - **Truncation risk:** a base64 body is exactly the payload shape this server cuts short (see the retry pattern below) — it's why the image transport was moved to names once before. `apply` is defensive about it: a body cut mid-base64 fails to decode and falls back to the name/placeholder instead of showing garbage, and a short read throws and is retried. Be especially wary of putting `imageBase64` in the **`GET /vehicles` list** payload — that multiplies one photo's size by the fleet in a single response. Per-id via `/vehicles/image` is the safer place for it, at the cost of placeholder-only list rows.
- **Retry pattern:** the C++ server intermittently truncates responses (`"unexpected end of stream"` — it needs a `sendAll()` loop + graceful socket close). As a workaround, the idempotent GETs and login retry up to 3 attempts (`*_MAX_ATTEMPTS`). Keep this in mind before "fixing" client networking — the root cause is server-side.
- **No connection reuse:** the server also mishandles HTTP keep-alive (it closes the socket after each response). OkHttp would otherwise pool and reuse that socket for the next request — most visibly the vehicles GET right after the login POST — which then fails with `"unexpected end of stream"`. `util/ApiClient` therefore forces a fresh connection per request (`Connection: close` header + a zero-idle `ConnectionPool`). This is what actually removed the intermittent first-fetch-after-login error; the retry loops are a secondary safety net.
- **Edge-to-edge and the keyboard:** `targetSdk 36` means content draws under the system bars by default, so every screen calls **`util/ScreenInsets.apply(view)`** — the single inset listener, unioning `systemBars() | displayCutout() | ime()`. Without it a top control (e.g. a back button) ends up untappable under the status bar, **and the keyboard covers the field being typed into**: edge-to-edge makes the app own its insets, so `android:windowSoftInputMode="adjustResize"` no longer resizes the window and adding it to the manifest fixes nothing. Bottom padding is `max(bars.bottom, ime.bottom)`, never the sum — the keyboard covers the navigation bar rather than stacking above it. `apply` also scrolls the focused field back into view when the IME opens (it aims at the enclosing `TextInputLayout`, so the counter/helper/error text stays visible, and posts the scroll because the padding only lands on the next layout pass). **Pass the scrolling container, not always the root:** on `activity_login.xml`/`activity_register.xml` it goes to `#loginContent`/`#regContent`, because padding the root would inset the full-bleed background photo and leave bars of raw window colour down the edges.
